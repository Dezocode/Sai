# Sai prototype lane enforcement
Status: **draft implementation contract for `prototype/lane-enforcement`**. Base authority: merged PR #75 on `main` at `759d017a6c6cec3960c158bb5f1e8906c200d740` (branch point); initial contract head `8a9616a8d3e01f9e8e03cbf5d7a1303aef13452f` (contract-only; never ready/merge on it alone).
## Goal
Make the prototype-plugin lane promised by PR #75 mechanically real without weakening any production Sai authority boundary. After merge, a successor may create SwiftUI code under `prototypes/plugins/<plugin>/` while `featureUIAllowed=false` stays in force for production. This PR builds the enforcement boundary Sai Author depends on — **not** Sai Author itself.
## Product/design intent
Sai Author is expected eventually to become a plugin feature inside Sai; prototype code must be **Sai-first by default**: reuse `SaiDesignLanguage` tokens/components/layout/motion/accessibility/typography/spacing/color/control states wherever they fit; reuse `SaiFoundation`/`SaiAPI` where that preserves the client/domain boundary; never clone production tokens into the prototype for speed; never bless a one-off by editing production design authority. Experimentation lives only in a plugin-local `PrototypeDesign/` scope; a prototype-local primitive is discovery evidence, graduated deliberately into `SaiDesignLanguage` under normal production review. Flow: `reuse SaiDesignLanguage -> isolate missing experimental primitive -> validate -> upstream reusable primitive -> integrate as Sai plugin`.
## Required implementation
1. **Verifier-owned canonical prototype root** — exactly `prototypes/plugins/`, owned by verifier code (not candidate JSON, plugin metadata, env, build settings). Path matching fails closed against `prototypes/plugin/`, `prototypes/plugins-evil/`, `prototype/plugins/`, `../` traversal/normalization escaping the root, symlink/filesystem indirection, root-level symlinks, direct children of the root, and candidate configuration that moves or widens the tree. No broad `prototypes/**` or repo-wide SwiftUI exemption.
2. **Production draft UI lock preserved** — `featureUIAllowed=false` unchanged; production restrictions continue for `apps/apple/**` and every non-prototype Swift source (`SaiFeatures`, `SaiFoundation`, arbitrary root Swift files stay illegal SwiftUI surfaces). Negative tests prove the old production failures still fail.
3. **Design-language inheritance, narrow escape hatch** — default prototype feature/view code obeys the raw-value design policy and consumes `SaiDesignLanguage`; temporary experimental visual values only inside `prototypes/plugins/<plugin>/PrototypeDesign/` (exploratory, not authority, not importable by shipping targets; manifest cannot nominate other exempt paths). Tests prove: Sai-primitive prototype passes; raw literals in ordinary prototype code fail; the same literal in `PrototypeDesign/` passes; near-prefix/out-of-lane `PrototypeDesign` fails.
4. **Mechanical one-way dependency isolation (Swift and Go)** — inspect production Apple package/build manifests (`apps/apple/Package.swift`, SaiKit package graph) with normalized/resolved paths so `../../../prototypes/plugins/author` cannot bypass; extend protection to new manifest formats before they can reference prototype code. For Go: prototype code may import/reuse stable production packages from `main`; production (`cmd/sai/**`, `internal/**`, shipping surfaces) must never import or require `prototypes/**` directly or transitively (source scan plus module-graph guard: a `go.mod` replace targeting the lane fails closed, every syntactic form). Prototype-focused work must not edit/fork/shadow production Go; such changes belong in a separate production-authority PR.
5. **Third lane rule: prototype PRs never edit protected production Go** — mechanical trusted-base diff gate: BASE -> candidate -> does a prototype-scoped change (any diff path under `prototypes/`) touch protected production Go (`cmd/sai/**`, `internal/**`)? yes -> FAIL. This is a diff-vs-base rule, not an AST rule about prototype constructs; prototype-local `func init()` is not proof of editing production Go. Verifiers (`cmd/sai-design-check/**`, `cmd/sai-verify/**`) are not protected production Go. Adversarial: prototype-scoped PR editing `cmd/sai/main.go`/`internal/**` with zero `init()`/`plugin.Open` FAILs; pure prototype-only PR PASSes; production->prototype import still FAILs; space-bearing protected filenames cannot evade path parsing; renamed/moved protected files must expose BOTH diff paths.
6. **Go/OpenAPI authority intact** — no second production domain architecture under the prototype root; interaction code may use mocks/local exploratory state, but behavior intended to graduate converges on the typed API/client boundary and Go domain model.
7. **`sai-verify` owns the surface** — add the prototype root to the verifier path grammar without widening unrelated roots; canonical feature-map entry; map the implementation and future plugin root; preserve trusted-BASE anti-weakening semantics; legal proof recipes only; introducing an unmapped prototype surface must not silently pass completeness; regression proving near-prefix paths are not canonical.
8. **CI triggers on prototypes** — the existing **Sai Design Language** workflow runs on `prototypes/**` changes; one externally visible design authority check, no competing second status; repository-wide Go and verification gates stay green.
9. **No Author shell here** — the immediate successor is `prototype/sai-author-shell`.
## Required adversarial acceptance matrix
**FAIL**: production SwiftUI lock outside approved production authority; SwiftUI lookalikes under `prototypes/plugin(s-evil)/`, `prototype/plugins`; candidate JSON relocating/widening the prototype root; prototype symlink/path escape outside the canonical root; raw design literal in ordinary prototype view code; `PrototypeDesign` outside a canonical plugin root; production Package.swift path resolving into the prototype tree; prototype-scoped PR editing protected production Go (`cmd/sai/**`, `internal/**`) incl. rename evasion; production Go importing `prototypes/**` (or a prototype PR adding such an import). **PASS**: SwiftUI under `prototypes/plugins/author/...`; normal prototype view using Sai Design Language primitives; experimental primitive in canonical plugin `PrototypeDesign/`; pure prototype-only PR; prototype package depending on approved shared SaiKit modules (once shell exists); prototype root represented in the `sai-verify` map (unmapped surface = FAIL). Never weaken a test to make CI green; if a requirement proves technically incompatible, stop and surface the conflict.
## Performance, modularity, scalability, density
Few verifier-owned constants/helpers over new manifests or parallel policy engines; reuse `cmd/sai-design-check` + `cmd/sai-verify` instead of a third checker; avoid duplicated path grammars (explicit root constant, cross-checked tests); linear-time checks cheap enough for every PR (walk-discovered manifests included); no production runtime dependency; stay under the repository PR addition budget; no generic plugin-platform abstractions until a real prototype requires them.
## Exact-head verification requirements
On every candidate HEAD run and preserve exact-head evidence: `go test ./cmd/sai-design-check/...`; `go run ./cmd/sai-design-check`; `go test -race ./...`; `go vet ./...`; current Sai Apple/SaiKit builds required by the design workflow; native `sai-verify` doctor/drive/proof; semantic hierarchy, agent audit, merge-handoff gates; the Sai Design Language check triggered by prototype paths. No stale-head success counts for a later SHA.

Owner-ready requires P0=P1=P2=0, no unresolved product/architecture/security findings, exact-head candidate CI and `sai-verify` preservation green. ## Explicit non-goals
No Author UI shell; no production feature-UI unlock; no marketplace/downloadable plugin loader; no JS/Wasm sandbox runtime; no move of domain/backend authority out of Go/OpenAPI; no Author persistence/collaboration/provider workflows; no wholesale Design Language redesign; no prototype-local visuals becoming production authority; no weakening of `sai-verify`, trusted-BASE preservation, or existing design checks.
## Handoff to `prototype/sai-author-shell` / definition of done
After merge, the next PR creates the smallest real continuation point under `prototypes/plugins/author/`: native SwiftUI package structure for macOS and iOS/iPadOS; editor + settings placeholders; default `SaiDesignLanguage`/SaiKit reuse; plugin-local `PrototypeDesign/` only where the language cannot express an experiment; macOS + Simulator build proof; `sai-verify` mapping/proof.
